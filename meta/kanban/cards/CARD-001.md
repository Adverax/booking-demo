## What to implement

Increment 1 opens with the contract: ADR-0009 requires the OpenAPI document before any handler, and the handoff names `api/openapi.yaml` as the first card of Increment 1.

- Write `api/openapi.yaml` describing the whole HTTP surface the requirements name: create, list and read a resource (FR-001, FR-002); free slots of a resource for a date range of at most 14 days (FR-003, FR-004); book one slot with a customer name and an idempotency key (FR-005, FR-006); read a booking (AC-029); cancel a booking by id (FR-007).
- Instants cross the boundary as RFC 3339 UTC strings (CON-001, CON-008). Weekly working hours follow ADR-0004: at most one interval per weekday, half-hour aligned bounds, inside one UTC day.
- Every error is a JSON object with a stable `code` field (CON-004). The codes are declared once, in the specification (ADR-0009): at least not found, validation error, slot taken (AC-018, AC-047) and idempotency-key conflict (ADR-0001, AC-038..AC-040), kept distinct.
- Generate the types and the `net/http` server interface from the document (ADR-0009 names oapi-codegen as the example generator), mounted on `http.ServeMux`, under `internal/httpapi/`, with the `go:generate` directive that reproduces it. No handler logic: handlers are implemented by the cards that own each behaviour.

Decided since the first cut, and declared by the contract:
- ADR-0018 (DEC-016 resolved): the contract declares the matching input constraints. An empty customer name (AC-052) and an empty idempotency key (AC-053) are rejected with a stable code, and so is an availability range whose start is after its end (AC-054). The range ordering cannot be expressed as a schema keyword: document it on the operation and its error response. Maximum lengths of names and keys are left to the API specification by FR-005 and FR-006 and no acceptance criterion tests them, so do not invent a figure.
- ADR-0016 (DEC-005 resolved): a slot is in the past when its start is earlier than the current time; a start equal to now is accepted. Describe the past-slot rejection that way.
- ADR-0020 (DEC-012 resolved): a past-slot rejection checks the idempotency key first. Describe the book operation's outcomes for a slot that has already started accordingly: a repeat of a stored key with the same payload returns the original booking as a success (AC-055), a repeat of a stored key with a different payload gets the idempotency-key conflict error, not the past-slot error (AC-056), and only a key with no stored booking gets the past-slot error (AC-057).

Open decisions this card must not answer (record them as TODO comments in the spec, do not invent constraints):
- DEC-011: the format of booking ids (guessable or not) is not decided; declare them as opaque strings.
- DEC-030: whether ADR-0009's rejection reason is restated on the drift argument. The decision itself is not reopened; contract-first stands.

## Failure matrix

Boundary owned by this card: the generated HTTP plumbing in `internal/httpapi` (request routing, parameter binding, body decoding, response encoding) wrapped by `httpapi.NewHandler`. It does no I/O of its own beyond the request and response, holds no state, starts no goroutine and retries nothing. Handler logic, the store and the server's timeouts belong to later cards (CARD-003..CARD-008) and are listed only to say where their bound is declared.

| Operation / boundary | Failure mode | Declared behavior | Bound |
|---|---|---|---|
| any route | unknown path, or a path not in canonical form (empty segment, `.`, `..`) that `http.ServeMux` would redirect | 404, JSON `{"code":"not_found"}`; `isCanonicalPath` is checked before routing, so no 3xx redirect is ever sent and no handler is called | 1 response per request, body < 128 B; 0 redirects |
| any route | known path, wrong method | 405, JSON `{"code":"method_not_allowed"}`, `Allow` header kept from `http.ServeMux` | 1 response per request |
| path/query binding | malformed parameter (date not `YYYY-MM-DD`, missing `from`/`to`) | 400, JSON `{"code":"validation_error"}`; the operation's handler is not called | 0 handler calls |
| JSON body decode (POST /resources, POST /bookings = `jsonBodyRoutes`) | body that is not exactly one JSON value: empty, malformed, or a valid value followed by trailing data (poison input) | `NewHandler` reads the whole body and rejects it unless `json.Valid(body)`: 400, JSON `{"code":"validation_error"}`; handler not called. A well-formed value of the wrong type is rejected by the generated decoder: 400 `validation_error`; handler not called | 0 handler calls |
| JSON body decode | body larger than `maxRequestBodyBytes` | `io.ReadAll` through `http.MaxBytesReader` stops at the cap before any decode; 413, JSON `{"code":"request_too_large"}`; handler not called. Routes without a request body never read it | bytes read per request <= `maxRequestBodyBytes` + 1 = 1 MiB + 1 B; body held in memory once (< 2 MiB buffer capacity) |
| handler (later cards) | returns an error not mapped to a declared response | 500, JSON `{"code":"internal_error"}`, the error text is not echoed | 1 response; 0 internal detail in body |
| handler (later cards) | panics | recovered; 500 JSON `{"code":"internal_error"}` if nothing was written yet; `http.ErrAbortHandler` is re-panicked so net/http aborts the connection as designed. The recovered value and stack are not recorded anywhere: TODO(DEC-010) at the recover site, logging undecided | 1 response or 1 aborted connection per request; process keeps serving; 0 log lines |
| response encode | encoding fails after the status line was written | status already sent cannot be changed; the connection carries a truncated body; no second status line is attempted beyond net/http's own guard | 1 truncated response per failure |
| duplicate delivery of POST /bookings | retry with the same `idempotencyKey` | declared by the contract (FR-006, ADR-0001, ADR-0020): same payload -> 200 with the original booking; different payload -> 409 `idempotency_key_conflict`; enforced by CARD-005 | 0 extra bookings per retry (CARD-005 tests) |
| duplicate delivery of POST /bookings/{id}/cancel | repeated cancel | 200 with the cancelled booking (ADR-0003); enforced by CARD-004 | 0 state changes after the first cancel |
| timeout, slow client, graceful shutdown | read/write/idle timeouts, drain on SIGTERM | not in this card: the `http.Server` is built by COMP-007 (CARD-003); this card adds no blocking call, so a request's time inside the plumbing is bounded by reading, validating (`json.Valid`) and decoding <= 1 MiB | plumbing adds O(body size) CPU (two passes over the body), no wait beyond reading it |
| non-cooperative handler (ignores ctx cancellation) | client gone / server shutdown | not in this card (no handler logic); the plumbing passes `r.Context()` unchanged to the handler | — |

- STRUCTURE: working hours are an array of `{weekday, start, end}` (1..7 items), not an object keyed by weekday: with an object a duplicate `monday` key would decode last-wins and AC-034 (two Monday intervals rejected) could not be detected. - STRUCTURE: availability range = query `from`, `to` as UTC dates (`format: date`), both inclusive; 14 days counting both ends (`to` at most `from` + 13); `from` after `to` rejected. Both rules are on the operation description (no schema keyword exists), per ADR-0018.
- STRUCTURE: schema keywords (`minLength: 1`, patterns, enums, minItems) are declarative contract for the consumer; there is no runtime schema validator (it would add kin-openapi to the binary).
