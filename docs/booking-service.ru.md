# Сервис бронирования — описание на русском с пояснениями

> Это пояснительный перевод документа `booking-service.md` (дизайн-бриф). Оригинал заморожен и остаётся источником истины; при расхождениях верен он.

## Что это за сервис

Небольшой бэкенд, который позволяет бизнесу опубликовать, когда доступны его ресурсы, а клиентам — забронировать временные слоты **без двойных бронирований**.

Бриф заморожен для живой демонстрации: всё, что в нём не написано, находится вне объёма работ.

## Контекст

Студия разрабатывает продукт для бронирования для небольшого бизнеса (клиника, коворкинг, барбершоп). Студия владеет фронтендом и отношениями с клиентом. Этот сервис — бэкенд, доступный **только через HTTP API**.

*Пояснение:* у сервиса нет собственного интерфейса; всё общение идёт через API, который вызывает фронтенд студии.

## Пользователи

| Роль | Кто это | Что делает |
|---|---|---|
| **Оператор** | Сотрудник бизнеса | Создаёт ресурсы и задаёт их рабочие часы |
| **Клиент** | Тот, кто записывается | Бронирует и отменяет слоты через фронтенд студии |

*Пояснение:* клиент не обращается к API напрямую — фронтенд вызывает API от его имени.

## Возможности

### 1. Ресурсы
Оператор создаёт ресурс (специалист, кабинет, рабочее место) с названием и **недельным расписанием**, например «пн–пт, 09:00–17:00». Ресурсы можно получить списком и по одному.

### 2. Доступность
Для ресурса и диапазона дат **не длиннее 14 дней** сервис возвращает свободные слоты.

- Слот длится **30 минут** и выровнен по half-hour (начинается в :00 или :30).
- Слот свободен, если он попадает в рабочие часы и не пересекается с **активным** бронированием.

*Пояснение:* «активное» — то, что не отменено. Отменённые брони слот не занимают.

### 3. Бронирование
Клиент бронирует **один слот** ресурса, указывая имя клиента и **ключ идемпотентности**. Сервис возвращает бронирование.

*Пояснение:* ключ идемпотентности — уникальная строка, которую присылает вызывающая сторона. Он нужен, чтобы при повторной отправке того же запроса (например, из-за сетевого сбоя) не появилось второй брони.

### 4. Отмена
Бронирование можно отменить. Отменённое бронирование **сразу освобождает слот**.

## Правила, которые должны выполняться всегда (инварианты)

1. **Нет двойных бронирований.** Две активные брони одного ресурса никогда не пересекаются — в том числе при одновременных запросах.
   *Пояснение:* это самое трудное правило, потому что оно должно держаться и в гонке: если приходят два запроса на один слот одновременно, успешным должен быть ровно один.
2. **Бронировать можно только доступное.** Бронь принимается только на слот, который попадает в рабочие часы и **не находится в прошлом**.
3. **Идемпотентность.** Повтор запроса с тем же ключом возвращает исходное бронирование и ничего нового не создаёт.
4. **Отмена необратима.** Отменённую бронь нельзя восстановить; нужно создать новую.

## Уже принятые решения

- Go 1.26, HTTP-слой на стандартной библиотеке `net/http`.
- Единственное хранилище — SQLite через чисто-Go драйвер (**без cgo**).
- Все времена хранятся и возвращаются в **UTC** в формате RFC 3339 (например, `2026-10-22T09:30:00Z`).
- JSON поверх HTTP; ошибки — JSON-объект со **стабильным полем `code`**.
  *Пояснение:* `code` — машиночитаемый идентификатор ошибки, который не меняется между версиями, чтобы фронтенд мог на него опираться.
- Один бинарник, настройка через переменные окружения.
- **Без аутентификации:** сервис работает за собственным шлюзом студии, который отвечает за доступ.

## Вне объёма (out of scope)

- Аутентификация и учётные записи.
- Платежи, депозиты, цены.
- Уведомления (email, SMS, напоминания).
- Повторяющиеся и многослотовые брони, часовые пояса кроме UTC.
- Праздники и исключения из рабочих часов на конкретные даты.
- Любой пользовательский интерфейс.

## На потом (не сейчас)

- **Лист ожидания.** Если слот занят, клиент может встать в очередь и будет автоматически забронирован, когда слот освободится после отмены.

*Пояснение:* это тоже вне объёма первого релиза и не должно реализовываться сейчас.

## Критерии успеха первого релиза

- Полный API работает от начала до конца на чистой базе данных.
- Тест на конкурентность отправляет **50 одновременных запросов** на бронь одного слота, и успешным оказывается **ровно один**.
- Каждое правило из раздела «Правила, которые должны выполняться всегда» покрыто хотя бы одним **именованным тестом**.

## Краткая шпаргалка

| Тема | Значение |
|---|---|
| Длина слота | 30 минут, по границе получаса |
| Окно запроса доступности | до 14 дней |
| Время | только UTC, RFC 3339 |
| Хранилище | SQLite, без cgo |
| Доступ | без аутентификации, за шлюзом |
| Ошибки | JSON с полем `code` |
| Главный тест | 50 параллельных броней → успех ровно одной |
